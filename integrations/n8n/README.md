# Calnode tools for n8n

The first tool is an authenticated **create_booking webhook**. It uses the existing Calnode REST API; no backend changes or hardcoded specialist/question IDs are needed.

## Import and configure

1. Import `create_booking.workflow.json` into n8n.
2. Open **Validate input**. Check the three defaults at the top: `base_url` (currently `https://emdeu-calnode.usekvi.com`), `timezone` (`Asia/Qyzylorda`), and `language` (`ru-RU`). Use the URL of the Calnode instance with phone-contact support deployed.
3. Open **create_booking**, the Webhook trigger. Authentication is set to **Header Auth**. Create/select an **HTTP Header Auth** credential with name `X-Calnode-Tool-Key` and a random secret value. Configure the caller to send that header. The secret is intentionally absent from the export; select a credential before running/publishing.
4. Use **Listen for test event**, copy n8n's Test URL, and send a request using a disposable available slot. This POST creates a real booking. The included local tests do not make network requests or create bookings.
5. Once configured, publish/activate the workflow and give the caller n8n's **Production URL**. The path is `/webhook/calnode/create_booking`; use the URL n8n displays if your installation has a custom prefix.

Calnode's question lookup and booking creation endpoints are public, so this workflow does not need a Calnode API key. The webhook secret protects this n8n tool endpoint; it is separate from a Calnode API key. Future admin list/cancel/reschedule tools will need their own authenticated Calnode access or an explicitly supplied manage capability.

## Request

```http
POST https://YOUR-N8N-HOST/webhook/calnode/create_booking
Content-Type: application/json
X-Calnode-Tool-Key: <configured-secret>
```

```json
{
  "request_id": "a-stable-unique-id-for-this-booking-intent",
  "event_type_slug": "replace-with-calnode-event-slug",
  "start_at": "2026-11-02T09:00:00+05:00",
  "name": "Иван Иванов",
  "contact_phone": "+77011234567",
  "procedure": "Консультация",
  "notes": "Первый визит",
  "timezone": "Asia/Qyzylorda"
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `request_id` | Yes, unless supplied as `Idempotency-Key` header | Stable unique ID, 1–200 characters, generated by the caller for one booking intent |
| `event_type_slug` | Yes | Event slug from its Calnode booking URL, not its display name or database ID |
| `start_at` | Yes | Exact appointment time, RFC3339 including offset or `Z`; use a slot offered by Calnode |
| `name` | Yes | Client name |
| `contact_phone` | Yes | International phone including `+` and country code; display separators are normalized |
| `procedure` | Yes | Answer to the event's required procedure question |
| `notes` | No | Answer to its optional notes question; omitted when empty |
| `timezone` | No | IANA timezone; defaults to `Asia/Qyzylorda` |
| `language` | No | Calnode locale; defaults to `ru-RU` |

The example time `09:00:00+05:00` is 09:00 local / 04:00 UTC. Change the sample event slug, procedure, client details, and time before sending it. This tool always uses phone as the primary contact and does not request email.

## How questions and specialists are selected

The workflow fetches `GET /v1/event-types/{slug}/questions` on every call. Your event must have exactly two questions:

- One **required** question of type Text or Dropdown: receives `procedure`.
- One **optional Text** question: receives `notes`.

Question labels, order, and IDs may differ for each event. IDs are resolved from the required/type flags, not guessed from Russian/English labels. If the configuration is ambiguous, the workflow returns an error before creating anything. For a dropdown, the procedure must exactly match an existing option.

The event must be active and public, and its contact policy must allow phone. Its hosts, availability, buffers, notice period, duration, limits, and routing remain configured in Calnode. The workflow sends **no host or specialist ID**.

With exactly one eligible host, Calnode assigns that specialist. If an event has several eligible specialists and you want one selected, set its routing mode to **round_robin** and choose the strategy in Calnode. Fixed/collective routing with several hosts has different semantics; n8n does not override it.

## Results

A free booking returns HTTP `201`:

```json
{
  "success": true,
  "status": "confirmed",
  "booking": {
    "id": "<Calnode-booking-id>",
    "event_type_id": "<Calnode-event-id>",
    "start_at": "2026-11-02T04:00:00Z",
    "end_at": "2026-11-02T04:25:00Z",
    "contact_method": "phone",
    "host_id": "<specialist-chosen-by-Calnode>",
    "hosts": [{ "id": "<specialist-chosen-by-Calnode>", "name": "<specialist-name>" }],
    "location_type": "in_person",
    "location_value": "<meeting-location>",
    "manage_url": "https://YOUR-CALNODE-HOST/manage/<private-token>"
  }
}
```

Duration comes from the event; the example shows 25 minutes. Calendar-generated video links may finish asynchronously—use the private manage page for final details. Keep the booking ID for subsequent tools, and give the manage link only to its intended client. No SMS is sent by this workflow.

Paid events return HTTP `202` with `status: "payment_required"`, `booking_id`, and `checkout_url`. This is a payment hold, not confirmation of a completed booking. Send the checkout link to the client; Stripe may request billing email.

Errors use `{ "success": false, "error": { "code": "...", "message": "..." } }` (some also include `retryable`). Authentication failures are generated directly by n8n before workflow execution.

| HTTP | Typical meaning |
| --- | --- |
| 400 | Missing/invalid input or invalid dropdown option |
| 404 | Event missing, inactive, or private |
| 409 | Slot unavailable, or a request with that idempotency key is still running; inspect the message |
| 422 | Question configuration, active-booking limit, or reuse of a request ID with different data; inspect the message |
| 429 | Calnode rate limit |
| 502/503 | Upstream error/unavailable service; a network timeout can leave the outcome unknown |

## Retrying safely

Generate one request ID in the calling application for each user-confirmed booking intent. Reuse the **same ID and identical data** after a network timeout or transient failure. Do not let an AI invent a new request ID for every attempt. Do not change to a different slot or procedure under the same ID after success.

The workflow forwards a namespaced `Idempotency-Key` to Calnode. Calnode replays a completed request or rejects a conflicting/in-progress one. Its worker expires idempotency records after approximately 24 hours; this is not permanent deduplication. Reconcile the booking before replaying an old uncertain request after that window. A changed/deleted question configuration can also prevent retrying the same input unchanged.

## Local maintenance checks

The Code node sources are in `create-booking/`. After editing them, regenerate the import file and run its offline checks:

```text
node integrations/n8n/create-booking/build-workflow.mjs
node --test integrations/n8n/create-booking/workflow.test.mjs
```

The export disables saved production execution payloads and manual execution persistence because requests contain client contact/notes and responses contain private manage links. It is imported inactive and contains no credentials. Publishing, configuring a real credential, and a live n8n smoke test must be done on your instance; the offline checks do not certify its node/runtime version.
